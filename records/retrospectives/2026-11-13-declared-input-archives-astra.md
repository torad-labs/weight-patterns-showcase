## Decision and reason

A remotely verified, exactly identified archive can fulfill the retained-input purpose for historical run records. Permanent local residency is not the scientific invariant; recoverability and unchanged identity are. I accept that storage direction, but not a shape-only exception based on a boolean receipt. The existing verifier remains in force until the implementation preserves the following distinctions.

1. A retained archive identifies the exact repository-relative input, every included file's relative path, byte count and SHA-256, and the corresponding bucket location. The successful remote-byte verification belongs to that inventory, not merely to a directory name or an upload receipt. Declared child files need exact membership; unrelated, partial, stale or path-escaping records cannot satisfy them.
2. An archived directory must be checked even when its directory and metadata remain locally. The current `path.exists()` test would otherwise accept a hollow directory without examining the archive. A missing child may be covered by an ancestor inventory only when that child's exact identity is present.
3. Archival must not skip the current allowed-root, source-run, target-source or original-model identity checks. `target_source` has a separate existence check today. Local declarations, results, parameter-source records and archive metadata remain readable so that historical claims do not disappear behind an archive marker.
4. Historical reproducibility and immediate execution readiness are separate. The global record verifier may recognize a valid archive; native preflight must require the chosen run's actual declared inputs and target to be restored and verified before computation starts. It must not silently accept an archived active input and defer failure to a later file read. No automatic network operation is added to every commit.
5. Restore uses the recorded inventory and checks returned bytes without overwriting unrelated local work. A failed or incomplete restore is not a ready input. Existing upload/read-back-before-release requirements remain unchanged.

No periodic bucket-check cadence or numerical retry policy is introduced. Verification belongs to the concrete archive/release and restore operations. An offline record check cannot claim that a remote object still exists now merely because its earlier read-back passed; execution establishes availability through restoration.

## Partial-release error repaired without touching archived data

Source review found that `release` called `os.unlink` without catching an ordinary filesystem error. A later readable but non-writable directory can pass the file-identity checks, allow earlier removals, then raise `PermissionError` before the partial-release receipt is written. That loses the operation's accounting, not the bound archive's recoverability, and does not invalidate the three successful complete receipts above.

A focused temporary-filesystem regression reproduced the unhandled `PermissionError` after two files were removed. The repair catches `OSError`, stops at that file, records the completed removals and the error, returns the problem, and retains the readiness receipt needed to identify remaining files. The same test then passes, including resumption after the permission issue is removed: two removals and then one, both recorded. It uses a stand-in bucket and `/tmp`, never the study's archived files. Abrupt process termination or machine failure can still interrupt bookkeeping; no transactional/crash-safe guarantee is made.

Checks: all 23 archive tests and all 10 round-two verifier tests pass. The initial combined test command used the nonexistent module `tests.test_verify_round2`; the archive tests passed in that invocation, and the corrected `tests.test_round2_verifier` command passed separately.
